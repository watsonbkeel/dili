# 本地历史导览小程序：从原型到可测试版本的迭代教学复盘

> 整理日期：2026-07-11
> 项目形态：微信小程序 + Node.js 后端
> 教学目的：帮助学生理解如何从连续的用户反馈中提炼需求、修改实现、保护部署契约、验证结果，并判断项目是否真的完成。

## 1. 文档说明

这不是一份单纯的功能清单，也不是把聊天内容原样复制下来。本文按真实开发过程重新组织了本轮对话，重点回答五个问题：

1. 项目最初有什么问题？
2. 用户为什么要求这样修改？
3. 开发时如何把自然语言需求转成数据结构、页面状态和接口？
4. 修改以后如何证明它生效，而不是只证明“代码写完了”？
5. 当前版本还存在哪些风险，需要继续做什么？

本文依据当前工作区和本轮对话整理。由于工作区尚未形成一个独立、干净的提交，文中“修改前”和“修改后”主要表示本轮迭代前后的产品行为，不等同于两个正式 Git 版本之间的精确差异。

## 2. 项目起点

项目在本轮开始时已经具有微信小程序和 Node 后端的基本结构，但不少页面仍停留在“能看到界面”的原型状态：

- 三种用户模式已经有页面雏形，但模式选择、返回逻辑和记忆行为不完整。
- 景点详情、路线、收藏、历史等页面存在按钮无效或数据不持久的问题。
- 视障模式只有简化首页，没有完整可用的景点详情和语音问答闭环。
- 行动不便模式使用大量静态演示文字，没有根据位置和景点数据计算推荐。
- 拍照识别返回统一演示信息，没有真正调用视觉模型。
- AI 助手能问答，但没有清楚携带“用户从哪里进入”的上下文。
- 部署已经在线，域名和端口是外部系统依赖，不能随意重建。

项目的核心架构如下：

```text
微信小程序
  |
  | HTTPS request / uploadFile
  v
https://dili.bkeel.com
  |
  | 香港服务器上的 Nginx 反向代理
  v
当前机器 13104 端口
  |
  v
Node.js 后端
  |-- 景点、路线、收藏相关数据
  |-- /api/assistant -> gpt-5.4-mini
  |-- /api/recognize -> gpt-5.6-terra
  |-- /api/transcriptions -> 本机 Qwen3 ASR
  `-- /assets -> 本地景点图片和无障碍地图
```

## 3. 本轮开发首先保护了什么

### 3.1 端口是部署契约，不是普通配置

对话最初对端口的记忆是“大于 10000，可能是 11304”，随后确认实际端口为 `13104`。最终核对结果是：

```text
local-history-guide.service
  -> backend/src/server.js
  -> LISTEN *:13104
```

域名 `https://dili.bkeel.com` 的 Nginx 上游已经指向该端口。因此本轮修改必须复用 `13104`，否则即使 Node 服务本身能启动，公网域名也会失效。

教学要点：

- 端口、域名、数据库表名、缓存 Key、对象存储路径都可能是外部契约。
- 在改代码前先用 `systemctl`、`ss` 和配置文件确认事实，不要只依据记忆。
- “换一个空闲端口能运行”不等于“部署正确”。

### 3.2 Nginx 和 frpc 的边界必须明确

用户特别说明：公网访问依赖 Nginx 反向代理，不依赖 frpc。本轮没有修改、停止或重启 frpc。

这类约束非常重要，因为“网络访问不通”经常诱使开发者同时修改多个网络组件，最后难以判断是哪一步造成故障。正确做法是只修改任务范围内的服务。

### 3.3 密钥不能进入前端和文档

小程序只请求自有后端，模型 API Key 由后端通过 `.env` 读取。本文只记录模型名和接口结构，不记录真实 Key。

当前模型分工：

| 用途 | 模型或服务 | 原因 |
| --- | --- | --- |
| 普通 AI 问答 | `gpt-5.4-mini` | 速度较快，适合旅行现场问答 |
| 图片识别 | `gpt-5.6-terra` | 用户反馈原模型识别准确率不足 |
| 语音转文字 | 本机 Qwen3 ASR | 录音不直接交给前端模型，统一走后端上传接口 |
| 文字转语音 | 微信 `WechatSI` 插件 | 与微信小程序运行环境直接集成 |

## 4. 需求是如何逐轮演进的

下表按产品问题而不是聊天消息数量归纳迭代过程。

| 阶段 | 用户反馈 | 核心判断 | 最终结果 |
| --- | --- | --- | --- |
| 1 | 新文档覆盖旧文档，担心原部署和 AI 失效 | 先确认现有部署契约和模型链路 | 保留 `13104`，Nginx 域名继续可用，未动 frpc |
| 2 | 视障首页点击景点没有下一页 | 不能只修点击事件，需要专用的低复杂度详情页 | 新增纯文字视障详情，自动播报，支持语音问 AI |
| 3 | 返回按钮和首页滚动后不可见 | 关键操作必须脱离普通文档流 | 固定顶部导航，并为正文预留占位空间 |
| 4 | 首次进入应选模式，之后记住选择 | 模式是用户偏好，需要持久化 | 模式选择成为首个页面，Storage 记住选择 |
| 5 | 视障首页语音搜索放在列表最后不方便 | “页面底部”不等于“内容末尾” | 语音搜索固定悬浮在首屏底部 |
| 6 | 拍照识别总是统一答案 | 原功能只是演示数据，不是真识别 | 接入真实视觉模型，升级为 `gpt-5.6-terra` |
| 7 | 图片识别需要地理位置 | 图像和位置联合能缩小候选范围 | 上传图片时同时发送经纬度和定位精度 |
| 8 | 我的路线不能编辑、删除、保存 | 页面状态没有可靠持久化模型 | 支持多路线 CRUD、改名、景点调整和智能排序 |
| 9 | 收藏、推荐、不推荐没有生效 | 需要明确的本地状态和后端计数契约 | 收藏按城市分组，推荐互斥、可取消、显示次数 |
| 10 | 浏览历史为空，收藏不能进入详情 | 页面间导航和记录时机缺失 | 详情加载时记历史，列表用 `navigateTo` 保留返回栈 |
| 11 | 加入路线只能加入当前路线 | 操作对象不应由系统隐式决定 | 弹出全部路线，可选择或新建路线 |
| 12 | 行动不便首页是静态假数据 | 推荐必须来自位置、步行时间和无障碍字段 | 30 个景点补数据，生成两类排序列表 |
| 13 | AI 助手不知道从哪个页面进入 | 上下文已经传 ID，但页面和预设没有使用 | 展示来源，并按景点/识别/模式生成问题预设 |
| 14 | AI 助手需要语音输入 | 复用现有录音、静音检测和 ASR 流程 | 文字/语音切换，3 秒静音自动提交并播报 |
| 15 | AI 播报按钮设计理解出现偏差 | 全局按钮无法播报历史消息 | 每条 AI 回复都有独立播报/暂停/续播按钮 |
| 16 | 明十三陵收藏被归入“其他城市” | 旧缓存缺字段，且占位值阻断了数据修复 | 按景点 ID 补全并回写，外地显示真实城市名 |

## 5. 三类用户模式

### 5.1 为什么不能只做一套页面再放大字体

普通用户、视障用户和行动不便用户的差异不只是颜色和字号，而是任务优先级不同：

- 普通用户需要图片、收藏、路线、推荐和丰富资料。
- 视障用户需要低操作复杂度、固定关键按钮、自动播报和纯文字信息。
- 行动不便用户首先关心无障碍通道、步行时长、距离和路线强度。

如果只给同一页面加 CSS 模式，复杂交互仍然存在，无法真正降低使用负担。因此本项目采用共享数据、分离关键页面的方案。

### 5.2 首次模式选择与记忆

当前 `miniprogram/app.json` 的第一页是：

```text
pages/mode-select/mode-select
```

用户第一次进入时选择模式；之后通过本地 Storage 读取上次选择，并直接进入对应首页。这样视障用户不需要每次重复寻找模式入口。

主要代码：

- `miniprogram/pages/mode-select/`
- `miniprogram/utils/userMode.js`
- `miniprogram/utils/navigation.js`
- `miniprogram/app.json`

教学要点：用户偏好和临时页面状态不同。偏好需要跨会话持久化，临时展开状态通常不需要。

## 6. 视障模式：从无效列表到完整语音流程

### 6.1 问题一：点击景点没有详情

原问题不是“缺少一个跳转”这么简单。普通详情包含大图、多个功能区和较复杂操作，不适合直接复用。

最终新增了独立页面：

```text
miniprogram/pages/low-vision-place/
```

页面特征：

- 白底黑字。
- 不显示图片。
- 景点资料按简介、历史、现场重点、参观提示和位置分类。
- 打开页面后自动播报景点介绍。
- 顶部返回按钮固定可见。
- 底部支持语音向 AI 提问。

### 6.2 问题二：固定返回不是简单加 `position: fixed`

固定导航以后，如果正文不增加顶部占位，第一段内容会被导航遮挡。因此实现同时包含：

```text
固定导航层
+ 与导航等高的正文占位层
+ 根据状态栏和胶囊按钮计算的安全距离
```

这是处理固定头部时的通用模式。

### 6.3 问题三：语音搜索放错了位置

第一次修改把“语音搜索”排在所有景点之后。从代码角度看它确实位于页面底部，但从用户体验看，用户必须先滚动很久才能使用，违背了视障模式“语音优先”的目标。

用户进一步澄清后，最终改为固定在首屏底部：

```text
position: fixed
bottom: 0
safe-area-inset-bottom
正文增加底部 padding
```

这次纠偏说明：

> 自然语言里的“页面底部”可能指视觉视口底部，也可能指文档内容末尾。开发前要结合用户任务判断，而不能只按字面实现。

### 6.4 语音搜索状态机

语音搜索和语音问答共享以下状态：

```text
idle
  -> requesting_permission
  -> recording
  -> processing
  -> transcribing
  -> searching / asking_ai
  -> result
  -> idle
```

静音判断不是等待固定录音时长，而是读取录音帧：

```js
if (frameContainsVoice(frameBuffer)) {
  lastVoiceAt = Date.now();
}

if (Date.now() - lastVoiceAt >= 3000) {
  stopRecording();
}
```

主要代码：

- `miniprogram/utils/voiceInput.js`
- `miniprogram/pages/low-vision-home/low-vision-home.js`
- `miniprogram/pages/low-vision-place/low-vision-place.js`
- `miniprogram/utils/api.js`
- `backend/src/services/transcription.js`

## 7. 拍照识别：从统一演示答案到真实视觉模型

### 7.1 原问题

用户上传不同图片时，页面返回相同结果。这说明页面展示已经存在，但识别结果来自固定演示对象，不来自图片内容。

### 7.2 修改思路

完整识别链路需要同时处理：

1. 小程序选择或拍摄图片。
2. 必要时压缩图片。
3. 获取 `gcj02` 位置。
4. 通过 `wx.uploadFile` 上传图片、纬度、经度和定位精度。
5. 后端把图片转换为模型可接受的输入。
6. 使用结构化提示词要求模型返回 JSON。
7. 对置信度、布尔字段和模型输出做容错解析。
8. 尝试关联本地已知景点 ID，以便继续进入详情。

### 7.3 为什么加入位置

单张建筑照片可能只包含屋顶、石雕或局部构件。加入位置以后，后端可以把附近已知景点作为候选提供给模型，降低把相似建筑识别成外地景点的概率。

最终视觉模型改为：

```text
gpt-5.6-terra
```

Key 和 Base URL 没有改变，问答模型仍为 `gpt-5.4-mini`。

主要代码：

- `miniprogram/pages/camera/`
- `miniprogram/pages/recognition-result/`
- `miniprogram/utils/api.js`
- `backend/src/services/recognition.js`
- `backend/src/config.js`
- `backend/src/server.js`

### 7.4 仍需验证

自动测试可以确认“图片和位置已进入模型请求”，但不能替代真实照片测试。仍应建立一组固定回归图片，例如故宫、天坛、明十三陵、普通街景和非景点图片，记录每张图片的预期结果和置信度范围。

## 8. 路线编辑：先建立状态模型，再做按钮

### 8.1 原问题

- 路线名称固定。
- 不能新增、切换或删除路线。
- 景点调整后重新进入页面会恢复原样。
- “智能排序”没有真实排序逻辑。
- “我的”页面中存在重复入口。

这些问题的共同根因不是按钮少，而是路线没有统一、可持久化的状态模型。

### 8.2 当前路线结构

路线状态被集中到 `miniprogram/utils/routeStore.js`，概念结构如下：

```js
{
  currentRouteId: 'route-id',
  routes: [
    {
      id: 'route-id',
      name: '路线名称',
      stops: []
    }
  ]
}
```

页面所有新增、删除、改名、顺序调整操作都经过同一个 Store 并立即写入 Storage。

### 8.3 智能排序不是“按一个字段排序”

当前版本采用简单、可解释的规则：

- 重要景点优先。
- 再考虑推荐游玩时长。
- 有定位时考虑当前位置和景点间距离。

这不是旅行商问题的最优解，但对教学版本更合适，因为规则可以被测试和解释。复杂算法应该在数据质量和业务目标明确后再引入。

### 8.4 从景点详情加入路线

“加入路线”不再默认加入当前路线，而是：

```text
打开路线选择面板
  -> 选择已有路线
  -> 或新建路线
  -> 检查重复景点
  -> 保存
```

主要代码：

- `miniprogram/pages/routes/`
- `miniprogram/utils/routeStore.js`
- `miniprogram/pages/place/place.js`

## 9. 收藏、推荐与浏览历史

### 9.1 收藏状态

详情页使用爱心表达收藏状态：

- 未收藏：灰色，“待收藏”。
- 已收藏：红色，“已收藏”。

收藏列表按城市分组，可进入详情，也可以快速删除。

### 9.2 明十三陵为什么进入“其他城市”

种子数据中的明十三陵本来就有：

```text
city: 北京
address: 北京市昌平区十三陵镇
```

真正的问题来自旧收藏缓存：早期保存的记录可能没有 `city` 和 `address`。旧实现遇到“其他城市”后直接接受该值，不再尝试修复。

最终策略是“读取时迁移”：

1. 把“其他城市”“未知城市”等当作占位值，不当作真实城市。
2. 优先检查收藏对象中的真实城市字段。
3. 尝试从地址提取城市。
4. 根据景点 ID 到本地 seed 中补全。
5. 把修复后的记录重新写回 Storage。

因此：

- 明十三陵旧收藏会恢复为“北京”。
- “成都市”统一显示为“成都”。
- 地址为“浙江省杭州市……”时显示“杭州”。
- 只有完全没有线索时才显示“其他城市”。

主要代码：`miniprogram/utils/favorites.js`。

教学要点：客户端 Storage 也是数据库。字段变更以后要考虑旧数据迁移，不能只保证新记录正确。

### 9.3 推荐和不推荐

推荐状态满足以下约束：

- 默认两个按钮都是灰色。
- 推荐和不推荐互斥。
- 再次点击当前选择会取消。
- 选择后按钮高亮。
- 后端记录次数，不验证身份。

这是一种适合演示版的计数方案，但不是防刷票方案。

### 9.4 浏览历史

浏览历史在成功打开景点详情时记录，而不是在列表点击时记录。这样可以避免请求失败的页面也进入历史。

历史按最近浏览时间排列；重复访问同一景点时移动到顶部，不重复创建多条记录。历史和收藏使用 `navigateTo` 打开详情，因此返回时仍保留原页面栈。

主要代码：

- `miniprogram/utils/viewHistory.js`
- `miniprogram/pages/history/`
- `miniprogram/pages/favorites/`
- `miniprogram/pages/place/place.js`

## 10. 行动不便模式：把静态演示改为数据驱动

### 10.1 定位策略

为了课堂和演示环境稳定，首次进入不立即弹出定位授权，而是使用天安门前长安街附近的演示坐标：

```js
{
  lat: 39.90746,
  lng: 116.39763
}
```

只有用户点击“刷新定位”时才调用真实定位：

```js
wx.getLocation({
  type: 'gcj02',
  isHighAccuracy: true
});
```

定位失败时页面明确显示仍在使用演示定位，而不是假装获得了真实位置。

### 10.2 数据补全

两份景点数据保持同步：

- `backend/data/beijing-hotspots.seed.json`
- `miniprogram/data/beijing-hotspots.seed.js`

当前 30 个景点全部包含：

```js
walkingTimeMinutes
walkingTimeNote
accessibility: {
  level,
  hasAccessibleRoute,
  label,
  wheelchairTourable,
  summary,
  mapUrl,
  sourceUrl,
  updatedAt,
  disclaimer
}
```

当前数据统计：

| 项目 | 数量 |
| --- | ---: |
| 景点总数 | 30 |
| 有图片 | 30 |
| 有步行时间 | 30 |
| 有无障碍信息 | 30 |
| 标记为可使用轮椅游览 | 25 |

### 10.3 无障碍景点排序

当前规则：

1. `full` 优先。
2. `partial` 其次。
3. 再按距离。
4. 距离相同时按步行时间。

不适合轮椅核心游览的景点不会进入该列表。

### 10.4 少步行推荐

当前使用简单评分：

```js
score = distanceMeters + walkingTimeMinutes * 80;
```

分数越低越靠前。这个公式不是医学建议，也不是精确路径规划，只是把“离当前位置近”和“景区内步行少”组合成一个可解释的演示算法。

主要代码：`miniprogram/utils/mobilityPlaces.js`。

### 10.5 详情页差异

- 只有行动不便模式在详情顶部显示无障碍信息。
- 故宫展示官方无障碍路线图，并支持点击放大。
- 页面保留免责声明，提醒设施可能随维护和开放区域变化。

## 11. AI 助手：上下文、语音输入与逐条播报

### 11.1 原问题：后端知道 ID，用户界面却不知道来源

景点详情进入 AI 页面时，前端已经保存了：

```js
{
  type: 'place',
  id: 'beijing-palace-museum'
}
```

但 AI 页面仍显示固定的故宫、天坛问题。这导致用户无法确认 AI 是否理解当前景点。

### 11.2 当前上下文设计

入口通过 `miniprogram/utils/navigation.js` 写入 `aiAssistantContext`。AI 页面再根据类型生成展示信息和预设问题。

示例：

```js
{
  type: 'place',
  id: 'beijing-palace-museum',
  name: '北京故宫',
  summary: '...',
  mode: 'mobility'
}
```

页面会显示：

```text
来源：北京故宫景点详情
正在了解：北京故宫
```

问题预设也会变为：

- 北京故宫的历史背景是什么？
- 到北京故宫现场最值得看什么？
- 北京故宫有哪些无障碍设施和少步行建议？
- 北京故宫大概需要多长时间游览？

拍照识别、城市首页、视障首页和行动不便首页都有各自的来源说明。

后端不仅接收页面文字，还会根据景点 ID 补充结构化事实：摘要、现场看点、预计步行时间和无障碍情况。

主要代码：

- `miniprogram/utils/assistantContext.js`
- `miniprogram/pages/assistant/assistant.js`
- `backend/src/services/assistant.js`

### 11.3 文字输入和语音输入切换

输入区提供文字/语音切换。语音流程是：

```text
开始
  -> 请求麦克风权限
  -> 录音
  -> 手动停止或连续静音 3 秒
  -> 上传到 /api/transcriptions
  -> 得到文字
  -> 自动提交 /api/assistant
  -> 显示并自动播报回答
```

### 11.4 播报按钮经历了两次设计纠偏

第一次实现：每条回复有一个很小的“播报”按钮，页面下方另有“暂停/继续/停止”三个按钮。问题是入口太小，而且功能重复。

第二次理解偏差：把所有控制合并成页面级大按钮，只能控制最近回复。这样虽然按钮简洁，但用户无法播报历史回复。

最终实现：每一条 AI 回复后面都有一个大按钮，该按钮独立绑定消息索引。

状态规则：

```text
未播放 -> 播报
播放中 -> 暂停
已暂停 -> 播报（点击后从暂停位置继续）
播放完成 -> 播报（从头重新播放该条）
```

如果正在播放回复 A，用户点击回复 B：

```text
停止 A 的播放队列
  -> 把 audioMessageIndex 切换为 B
  -> 生成并播放 B
```

这次纠偏的教学价值是：

> “减少按钮数量”不能破坏操作对象。消息级操作应该跟随消息，而不是被错误提升为页面级操作。

## 12. `app.json` 为什么也是功能代码

新增页面或调用隐私能力，只修改 `.js/.wxml/.wxss` 不够。微信编译器还需要在 `app.json` 中知道：

- 页面路径。
- 定位权限说明。
- 录音权限说明。
- 必需的私有信息类型。
- `WechatSI` 插件版本和 Provider。
- request、uploadFile 和 downloadFile 超时。

因此 `app.json` 的修改时间和内容是编译是否成功的重要证据，不能把它当作无关配置文件。

## 16. 本轮最值得学生学习的工程方法

### 16.1 先找根因，不按按钮逐个修

路线页面看似缺少多个按钮，根因却是没有持久化状态模型；收藏城市显示错误，根因是旧缓存迁移；AI 问题不相关，根因是上下文没有进入页面表达和问题生成。

### 16.2 把用户纠正视为需求澄清，不视为返工失败

语音搜索“放在底部”和 AI 播报“合并按钮”都出现了合理但错误的字面理解。用户纠正以后，应记录新的行为规则并增加测试，避免再次回退。

### 16.3 状态机比多个布尔值更容易解释

录音、AI 加载和语音播放都有明确阶段。即使页面数据仍使用若干布尔字段，开发时也应该先画出状态转换，检查哪些操作在每个状态下允许发生。

### 16.4 结构化数据优先于页面硬编码

步行时间、无障碍状态、城市、路线和 AI 上下文都应该进入结构化数据或 Store。页面只负责展示和触发操作，不应自行猜测事实。

### 16.5 部署验证必须经过真实访问路径

只访问 `localhost:13104` 不能证明 Nginx 和域名正常。最终验证必须经过：

```text
https://dili.bkeel.com -> Nginx -> 13104 -> Node
```

### 16.6 “测试通过”与“产品完成”不是同一句话

Node 测试擅长验证算法、数据和接口；微信真机测试负责验证权限、安全区、插件、触摸目标和实际声音。两者缺一不可。

## 18. 建议的课堂实践

### 练习一：为语音输入画状态图

要求学生列出权限拒绝、无声音、ASR 空结果、AI 超时、播放失败等异常分支，并指出页面应该显示什么。

### 练习二：调整少步行排序权重

把：

```js
distanceMeters + walkingTimeMinutes * 80
```

改成两个不同权重，比较排序结果，并解释哪类用户更适合哪个权重。

### 练习三：设计旧数据迁移

假设收藏记录以后新增 `province`、`country` 和 `sourceVersion`，要求设计不丢失旧收藏的升级方案。

### 练习四：建立图片识别回归集

选择 10 张已知景点、5 张相似建筑和 5 张非景点图片，记录有定位和无定位两种情况下的识别结果。

### 练习五：为 AI 播报写交互测试

覆盖：

- 播放回复 A。
- 暂停 A。
- 继续 A。
- 播放 B 并确认 A 停止。
- B 播放结束后重新播放 B。

本轮迭代把项目从“页面较完整但多处是静态演示或无效按钮”的状态，推进到了“核心流程有真实数据、可持久化、可调用 AI、可部署验证”的阶段。

最重要的成果并不是增加了多少按钮，而是建立了几条完整闭环：

