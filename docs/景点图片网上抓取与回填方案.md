# 景点图片网上抓取与回填方案

## 目标

为北京历史旅行导览小程序补充真实景点图片，避免使用生成图，避免小程序运行时直接热链外部图片。

最终效果：

- 首页景点卡片有封面图
- 景点详情页有头图或图片资料图
- 路线页可复用景点封面
- 图片文件存放在小程序本地目录或后续迁移到云存储/CDN
- 数据文件中的 `images[].url`、`coverImage` 能正常指向图片

## 基本原则

- 不在小程序端直接引用网页图片 URL，避免防盗链、合法域名、网络不稳定问题。
- 从国内可访问网页抓取图片，下载到本地。
- 优先使用景区官网、博物馆官网、北京旅游网等来源。
- 百度百科只作为兜底来源。
- 保留图片来源字段，便于后续维护。
- 第一版按教育演示用途处理，图片字段可标记为 `教育版演示使用`。

## 图片来源优先级

1. 景区或博物馆官网
   - 故宫博物院：https://www.dpm.org.cn/
   - 颐和园官网：https://www.summerpalace.net.cn/
   - 中国国家博物馆：https://www.chnmuseum.cn/
   - 恭王府博物馆：https://www.pgm.org.cn/

2. 北京旅游网
   - https://www.visitbeijing.com.cn/
   - 适合补充什刹海、景山、北海、胡同街区、南锣鼓巷等开放式景点。

3. 政府/文旅页面
   - 北京市文旅相关页面
   - 北京市政府英文/中文专题页面
   - 公园管理中心相关页面

4. 百度百科兜底
   - 用于官网和旅游网找不到合适图片的景点。
   - 优先抓词条首图或图册中的清晰横图。

## 本地文件目录

图片建议存放到：

```text
miniprogram/assets/images/attractions/
```

文件命名使用景点 ID：

```text
beijing-palace-museum.jpg
temple-of-heaven.jpg
jingshan-park.jpg
shichahai.jpg
summer-palace.jpg
```

如同一景点后续需要多图，可追加序号：

```text
beijing-palace-museum-1.jpg
beijing-palace-museum-2.jpg
```

## 数据回填位置

需要同步更新两个种子数据文件：

```text
backend/data/beijing-hotspots.seed.json
miniprogram/data/beijing-hotspots.seed.js
```

每个景点至少更新 `images[0].url`：

```json
{
  "url": "/assets/images/attractions/beijing-palace-museum.jpg",
  "caption": "北京故宫",
  "source": "故宫博物院官网",
  "sourceUrl": "https://www.dpm.org.cn/",
  "license": "教育版演示使用"
}
```

如果当前数据里 `coverImage` 是由 `images[0]` 推导出来的，只需要更新 `images[0]` 即可。

## 抓取脚本建议

建议新增脚本：

```text
scripts/fetch-attraction-images.js
```

脚本职责：

1. 读取一个图片来源清单。
2. 请求来源页面。
3. 提取候选图片 URL。
4. 下载图片到 `miniprogram/assets/images/attractions/`。
5. 压缩图片。
6. 更新两个种子数据文件。
7. 输出抓取报告。

## 来源清单结构建议

可以新增：

```text
scripts/attraction-image-sources.json
```

示例：

```json
[
  {
    "id": "beijing-palace-museum",
    "name": "北京故宫",
    "targetFile": "beijing-palace-museum.jpg",
    "sourceName": "故宫博物院官网",
    "sourceUrl": "https://www.dpm.org.cn/",
    "fallbackKeywords": ["北京故宫", "故宫博物院", "紫禁城"]
  }
]
```

## 图片提取优先级

脚本从页面中提取图片时，建议按以下顺序：

1. `meta[property="og:image"]`
2. `meta[name="twitter:image"]`
3. 页面中 `alt` 或 `title` 包含景点名称的 `<img>`
4. 页面主体区域第一张大图
5. 兜底使用人工配置的图片 URL

图片 URL 需要处理：

- 相对路径转绝对路径
- 去掉明显的图标、logo、二维码、小缩略图
- 优先选择宽度较大的图片
- 避免 base64 图片

## 图片规格

建议统一处理为：

- 格式：JPEG
- 宽度：约 1200px
- 比例：优先横图，建议 4:3 或 16:9
- 单张大小：150KB-300KB
- 文件名：英文景点 ID，避免中文路径

如果没有安装额外图片压缩依赖，第一版可以先下载原图，再人工或后续脚本压缩。

## 回填逻辑

脚本根据景点 `id` 找到对应数据项，更新：

```json
"images": [
  {
    "url": "/assets/images/attractions/{targetFile}",
    "caption": "{景点名称}",
    "source": "{sourceName}",
    "sourceUrl": "{sourceUrl}",
    "license": "教育版演示使用"
  }
]
```

注意：

- 不要删除原有 `summary`、`timeline`、`highlights`、`sources` 等字段。
- 只改图片相关字段。
- 两份种子数据要保持一致。

## 人工检查清单

每批抓取后需要人工快速检查：

- 图片是否确实对应景点
- 图片是否清晰
- 图片是否不是 logo、地图、二维码、人物头像
- 图片是否适合横向裁切
- 首页卡片是否正常显示
- 景点详情页头图是否正常显示
- 小程序包体是否明显变大

## 验收标准

第一批完成后应满足：

- 10 个核心景点都有本地封面图
- 首页景点列表能显示图片
- 景点详情页能显示图片
- 路线页封面或路线节点能复用图片
- 小程序不依赖外部图片热链
- 后端测试 `npm test` 通过
- 数据文件中保留 `source`、`sourceUrl`、`license` 字段

## 后续优化

如果图片数量增加导致小程序包体过大：

1. 将图片迁移到云存储或 CDN。
2. 数据中的 `url` 改为 HTTPS 图片地址。
3. 在微信公众平台配置合法下载域名。
4. 本地只保留少量默认占位图。
